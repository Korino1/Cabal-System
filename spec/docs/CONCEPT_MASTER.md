# Обобщённый концепт (Concept Master)

> Этот документ задаёт продуктовый и процессный концепт Cabal в режиме `MCP-only`.
> Runtime-канон исполняется программно через MCP и не читается моделями из файлов.

## 1) Первичные материалы (источники)
| Path | Type | Purpose |
| --- | --- | --- |

## 1.1) Приоритет источников
1) Runtime-канон в MCP (`Cabal Control Plane`) и `spec/docs/CONCEPT_MASTER.md` — первоисточники.
2) `spec/docs/CONCEPT_MATH_PROOF.md` — канон математических утверждений и ограничений.
3) Первичные материалы из списка выше — вторичные, только для верификации и синтеза.
4) Прочие файлы проекта — справочные.

## 2) Цель системы
- Создать `Cabal MCP-Only` как жёсткий управляющий слой для любой IDE и любой модели.
- Обеспечить единственный контур исполнения: модель может действовать только через MCP-методы Cabal.
- Перенести логику протокола (фазы, гейты, маршрутизация, правила, валидации) в программный уровень.
- Убрать зависимость качества от “прочитанных файлов логики” моделью: решения принимаются сервером политики, а не промптом.
- Сохранить переносимость: достаточно подключить MCP-сервер Cabal в IDE-клиенте.

## 3) Ключевые блоки и роли
### 3.1) Блоки Cabal Control Plane (MCP runtime)
- `Policy Registry`: версионируемые сквозные правила и ограничения исполнения.
- `Phase Engine`: конечный автомат фаз (C-0 → GA-1..GA-5 → ARCH → INTEGRATOR → ORCHESTRATOR).
- `Consult Router`: маршрутизация CONSULT по режимам `USER_TRACKING`/`YOLO`.
- `Task Graph Engine`: постановка, декомпозиция, зависимостный граф задач, статусы.
- `Agent Registry`: матрица агент/субагент → зоны ответственности, capability, допуски.
- `Gate Validator`: обязательные проверки Entry/Exit для каждой фазы.
- `Evidence Store`: структурированное хранилище артефактов, журналов и доказательств.
- `Audit/Event Log`: неизменяемый лог решений, вызовов, отклонений, дефектов.
- `Tool Proxy`: контролируемый доступ к инструментам (файлы, shell, внешние сервисы) через политику.

### 3.2) IDE-уровень
- IDE выступает MCP-клиентом и не содержит бизнес-логики протокола.
- Локальные файлы логики не являются источником инструкций для модели.
- Любая модель (LLM/агент) получает только структурированные ответы MCP.

### 3.3) Роли
- `User`: задаёт цель, ограничения, принимает развилки.
- `Orchestrator`: управляет назначениями и CONSULT-маршрутизацией.
- `Subagents`: решают узкие задачи по допускам.
- `Cabal MCP Runtime`: единственный обязательный слой управления и валидации.

## 4) Последовательность работы и взаимодействия
1. Пользователь подключает MCP-сервер Cabal в IDE и инициализирует сессию проекта.
2. Cabal загружает активный `policy_bundle` и фиксирует версию канона.
3. Любой запрос модели проходит через `Policy Registry + Phase Engine + Gate Validator`.
4. Cabal определяет допустимый этап, формирует задачу и назначает исполнителя.
5. Исполнитель получает только MCP-контекст (структурированные данные, разрешённые операции, ограничения).
6. Любые действия (чтение/запись/команды/интеграции) выполняются только через `Tool Proxy`.
7. Результаты валидируются гейтами, попадают в `Evidence Store`, события фиксируются в `Audit Log`.
8. При CONSULT:
   - `USER_TRACKING`: запрос уходит Пользователю;
   - `YOLO`: запрос уходит Оркестратору, который назначает субагента.
9. Переход фазы выполняется только после прохождения Entry/Exit проверок.

## 5) Ограничения и допущения
- Cabal обязателен как `single control plane` для логики проекта.
- Модели не имеют права обходить MCP и обращаться к “сырой логике” в файлах.
- Локальные документы схемы допускаются только для админов/разработчиков Cabal и аудита.
- Runtime-политика должна быть детерминированной и версионируемой.
- Любой MCP-клиент (IDE) считается тонким адаптером; управление остаётся на стороне Cabal.
- Любая попытка исполнения вне MCP-контроля считается нарушением протокола.

## 6) Сквозные правила (канон для каждого исполнителя на любой итерации)
Сквозные правила обязательны для всех ролей и всех этапов: концепт → схемы → функции → код → тесты → QA.

### 6.1) Категорические запреты (обязательное)
Запрещено:
- Выполнять проектные действия в обход MCP-сервера Cabal.
- Передавать моделям файлы логической схемы как источник инструкций к исполнению.
- Использовать “прямые” локальные инструкции, не прошедшие через Policy Registry.
- Менять фазу, статус, гейт или маршрут CONSULT без подтверждения Phase Engine.
- Применять незарегистрированные инструменты/серверы/интеграции.

### 6.2) Разрешённые инструменты и ограничения на зависимости (обязательное)
- Разрешён только MCP-контур Cabal как управляющий вход для моделей.
- IDE может использовать любые совместимые MCP-клиенты, но не подменяет политику Cabal.
- Внешние инструменты допустимы только через `Tool Proxy` и policy allowlist.
- Каноничные документы могут храниться в git, но runtime-логика берётся из MCP-реестра правил.

### 6.3) Запрет имитаций/упрощений в реализации (обязательное)
- Запрещены заглушки, псевдологика, фиктивные PASS/OK статусы.
- Запрещено “симулировать” прохождение фаз/гейтов без реальной валидации Cabal.
- Любое расхождение между заявленным состоянием и Audit/Evidence — дефект протокола.

### 6.4) ISA/SIMD/микроядра (если применимо)
- Базовый концепт Cabal независим от ISA.
- Для низкоуровневых проектов целевые ISA и fallback фиксируются отдельной policy-конфигурацией.
- Правила low-level проверок применяются через тот же MCP-контур и не обходят сквозные правила.

### 6.5) Мультиязычная математическая верификация (если применимо)
- Для математических частей сохраняется цикл RU → EN → ZH → DE → FR.
- Результаты синтеза фиксируются в структурированном виде в Evidence Store.
- Итоговые решения принимаются только после `math-critique` и явного выбора Пользователя.

### 6.6) Обновление канона после выбора Пользователя (обязательное)
- После выбора Пользователя и уточнения параметров обновление вносится:
  - в runtime-канон MCP (`Policy Registry` / параметры этапа C-0);
  - в зеркальные документы `spec/docs/CONCEPT_MASTER.md` и `spec/docs/CONCEPT_MATH_PROOF.md` для аудита.
- Переход в GA-1 запрещён до синхронизации runtime + зеркала.
- GA-5 не является местом изменения концепта.

### 6.7) Режим обработки CONSULT при старте GA-1 (обязательное)
- Перед первой постановкой задач в GA-1 Пользователь выбирает режим:
  - `USER_TRACKING`;
  - `YOLO`.
- Если выбран `YOLO`, до активации режима Оркестратор обязан запросить дополнительные сквозные правила.
- Режим активируется только после фиксации правил в runtime-каноне и журнале фазы.
- После активации `YOLO` каждый CONSULT уходит Оркестратору и назначается профильному исполнителю.

#### 6.7.1) Текущая конфигурация маршрутизации CONSULT
- mode: `USER_TRACKING` (default до явного выбора)
- yolo_additional_rules: `none`
- yolo_activated_at: `n/a`

### 6.8) Harness-протокол правок (обязательное)
- Для файловых правок разработчиками применяется `read -> hash verify -> apply`.
- Для runtime-политик применяется аналогичный принцип:
  - read policy revision;
  - verify expected revision/hash;
  - atomic apply.
- Изменения без проверки версии/хеша отклоняются.

### 6.9) Обязательное ознакомление со сквозными правилами перед каждой работой (обязательное)
- Перед каждой задачей любой агент/субагент обязан получить активный `policy_bundle` из MCP.
- Если правила расширены, исполнитель получает полный список (база + дополнения) до старта.
- Для `YOLO` Оркестратор обязан передавать полный `policy_bundle` в каждой CONSULT-постановке.
- Работа без актуального policy bundle считается нарушением протокола и оформляется как `CONSULT/DEFECT`.

## 7) Опросник для уточнения сквозных правил у Пользователя
Ответы фиксируются в runtime-policy и зеркалируются в этот документ.

- Какие категории действий запрещены в вашем проекте безусловно?
- Какие внешние сервисы/инструменты можно использовать через MCP, а какие запрещены?
- Какой режим CONSULT нужен на старте GA-1: `USER_TRACKING` или `YOLO`?
- Если `YOLO`, какие дополнительные правила маршрутизации и выбора исполнителей обязательны?
- Какие security/privacy ограничения обязательны (сеть, логи, хранение данных)?
- Какие гейты качества обязательны перед переходом фаз?
- Нужна ли обязательная multilingual-проверка для математических решений?

## 8) Перенос логики в программный уровень (MCP migration canon)
### 8.1) Целевое состояние
- Логика протокола хранится и исполняется в MCP runtime.
- Модели не читают логические markdown-файлы как инструкции.
- Файлы схемы остаются как human-audit зеркало, не как runtime-интерфейс модели.

### 8.2) Шаги миграции
1. Нормализовать правила/фазы/гейты в структурные схемы (`policy_bundle`, `phase_fsm`, `gate_rules`).
2. Загрузить схемы в MCP Registry с версионированием и immutable audit trail.
3. Перевести IDE-пайплайн на обязательные MCP вызовы для всех действий.
4. Отключить прямую подачу логических файлов в контекст модели.
5. Ввести runtime-проверки, блокирующие обход MCP.
6. Провести parity-check: runtime-решения должны соответствовать канону документов.

### 8.3) Критерии готовности
- Любое действие модели возможно только через MCP методы Cabal.
- Любой фазовый переход проходит только через Gate Validator.
- Любой CONSULT маршрутизируется через Consult Router.
- Любое отклонение фиксируется в Audit Log и поднимает дефект.
- Логика проекта воспроизводима через версии `policy_bundle` без чтения markdown моделью.
